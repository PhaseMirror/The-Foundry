## 1. Context
A formal substrate is needed to realize the recursive multiplicity dynamics described in the Genius v2 trajectory. This substrate must support prime-indexed state spaces and provide stable, contractive updates over time.

## 2. Decision
We implement the **PIRTM (Prime-Indexed Recursive Tensor Machine)** substrate:
1. **Multiplicity Cells:** The fundamental unit of state is the `MultiplicityCell`, which encapsulates prime-factorized tensors $|N\rangle$ in the ZSD Hilbert space $\mathcal{H}_\zeta$.
2. **Recursive Operator Updates:** Operators (e.g., $\Lambda_m$) act as recursive updates over tensor products with prime channels.
3. **Sparsity Enforcement:** We enforce a strict sparsity constraint ($P \le 12$) on the prime index set to maintain contractivity and computational efficiency.
4. **Phoenix Hooks:** Each cell provides hooks for the Phoenix-ℵ₀ reset matrix $\Xi_\phi$ to project transient states back into the lawful subspace $H_{lawful}$.

## 3. Alternatives Considered
- **Standard RNNs/LSTMs:** Rejected as they lack the prime-indexed structure and number-theoretic grounding required for zeta-guided optimization.
- **Dense Tensor Networks:** Rejected due to exponential complexity; prime-indexed sparsity provides a more efficient and mathematically structured alternative.

## 5. Risks
- **Complexity of Tensor Products:** Managing recursive tensor products can be computationally intensive and difficult to debug.
- **Boundary Stability:** Ensuring contractivity across recursive cycles requires rigorous spectral control.
