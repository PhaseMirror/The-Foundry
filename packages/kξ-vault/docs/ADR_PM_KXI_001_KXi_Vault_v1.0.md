# **0\. One sentence**

KΞ Vault is the display name for K3 local custody under a Foundry-modeled two-person receipt control plane. PrismPM compiles the model and supplies digest, sign, store, and verify. PrismPM is not the control plane. The vault remembers bytes. The second hand Accepts. Neither is the other.

# **1\. Claim, reflected without endorsement**

Inventor claim: call the project KΞ Vault and use PrismPM base functions as the two-person receipt control plane, then integrate that object into uor-foundry and publish it through foundry-web.

Operating fact already seated: PrismPM is a kiln of process law and a pinned SDK. Object A on PM-DIGI-001 is a two-person receipt control plane that can refuse a bind. K3 is content-address memory on a device the operator controls. K2 is a named other person, vacant by written refuse at 09:22 MDT. foundry-web publishes verified producer bytes and must not author product semantics.

The name can cover the join. The sentence that PrismPM is the quorum cannot.

# **2\. Central tension**

Stated intent: remember document bytes so they cannot be quietly rewritten, and require two hands before a bind. Operating incentive: treat a local hash, a portal View, or two PrismPM adapter calls as the second seat.

A vault that self-signs is K1 wearing a K2 coat. A compiler invoked twice from one credential slot is one keyboard. A published Pages asset that carries the signable bytes is a second store, not a View.

Secondary tensions, named: digest accuracy versus public-asset compliance; handwritten Lean velocity versus generated-only application safety; open local CLI versus hosted vault APIs.

# **3\. Decision**

1\. Display name is KΞ Vault. Module id is KXiVault. Prior shop title Prism Vault is retired as display only. Custody class remains K3. KΞ is not a fifth key seat.

2\. Three layers stay uncollapsed. Data plane: k3-vault directory. Control plane: Foundry LexLean predicates that refuse export and refuse vault-origin Accept. Tooling: PrismPM SDK and its adapters.

3\. PrismPM base adapters (digest, guest, random, sign, store, verify) are primitives. They are not persons. Two sign calls from one foundry-key slot count as one keyboard.

4\. Year-one increment is a new ObjectSpace class whose blobs remain on the operator directory. The portal View may read cid and receipt flags. It may not carry canonical 049c bytes, preimages, HMAC K, or private keys.

5\. A replicated Kappa object whose canonical bytes travel with the browser network is a later authority act. The product name does not imply it.

6\. 049c stays Proposed. HMAC-SHA256 remains the only live CRMF authenticator. Zero Poseidon2 live-seal sites on this module.

7\. Person column stays VACANT by the PM-K2-001 refuse. L.R., typed initials, architect phone, and prior-paper identification remain void.

8\. First producer path is src/Foundry/Storage/KXiVault.lex.tex. First publisher act is no-op on vault source until a verified producer revision exists.

### **8\.1\.2 Preimage schema, corrected**

The Blueprint's `preimage_v1` sets `"domain_separator": "049c_text_v1"`. That is refused — C-03. The corrected schema:

```json
{
  "$schema": "k3-vault/schema/preimage_v1.json",
  "preimage_id": "<uuid>",
  "cid": "<sha256>",
  "domain_separator": "PM-K2-ACCEPT-v1",
  "canonical_name": "049c_text_v1.txt",
  "created_utc": "<ISO8601>",
  "created_by": "K1",
  "state": "unsigned",
  "pinned": false,
  "export_eligible": false,
  "binding": {
    "adr": "PM-KXI-XXX",
    "receipt_required": true,
    "k2_seat_required": true,
    "architect_seat_required": null
  },
  "hmac_k": null,
  "signature_k1": null,
  "signature_k2": null
}
```

**Why the separator is vault-scoped and not transaction-scoped.** `049c` is a placeholder standing for a real future transaction, and the vault must exist *before* any transaction exists — otherwise the second seat has nowhere to sign. A protocol constant therefore cannot be named after a transaction: it would bind every later transaction's domain to whichever placeholder was written down first, and the vault could not be created ahead of its first use. So `domain_separator` stays the vault-scoped constant seated at §11, and the transaction name moves to `canonical_name`, which is display and provenance only and is read by no predicate.

This also means the schema is transaction-agnostic. The vault, its predicates, and its receipts are complete before any `049c` exists. Building the vault is not waiting on a transaction; a transaction is not waiting on a vault.

**`domain_separator` is a constant, not a field to be chosen per record.** A record that carries a separator outside the registered set is refused, not normalized. A domain that varies per record is not a domain separator, it is a field that defeats domain separation.

**`export_eligible` is a derived projection, never a gate.** The Blueprint lists it as a stored boolean with no statement of how it is computed. A stored boolean beside a predicate invites becoming a second, weaker door — write `true`, get export. So: `export_eligible` is written only by the producer as `mayExportPreimage(vaultState)`, it is never an input to that predicate, and on read disagreement the predicate wins. The invariant the Blueprint states — `hmac_k` stays `null` until both signatures are present — holds, and is extended: `export_eligible` stays `false` until `pinned ∧ pinAdrPresent ∧ acceptPath = 049c`, and `hmac_k` stays `null` until additionally both signatures verify against two distinct pubkeys.

**`architect_seat_required` is `null`, not `true`.** §4 records the Architect door as UNCLEAR. The Blueprint asserts the requirement in §1.2 and then asks in §9 whether it should be required. That is a decision, and this paper does not make it by schema default. `null` means undecided, and the schema validator refuses to treat `null` as satisfied or as refused.

### **8\.1\.3 Integrity chain, corrected**

Blueprint §1.4 step 5 verifies `vault.json.lock.n == audit.operations.log.n`. A count match does not verify content: an attacker with write access to both files edits the log and the count still agrees. Corrected:

```
on every mutating operation:
  1. k3 store -> CID computed -> blobs/<hash> written
  2. append to audit/operations.log:
       {op, cid, timestamp, actor, prev_op_hash, op_hash}
     where op_hash = SHA256(op || prev_op_hash)
  3. update blobs/index.json: {cid, size, mime, created}
  4. refresh vault.json.lock:
       {cid_root, op_count, op_chain_hash, prev_lock_cid}
     where op_chain_hash = SHA256(prev_op_chain_hash || op_hash)
  5. verify: op_count == operations.log length
     AND op_chain_hash == fold over operations.log of op_hash
     AND vault.json.lock.prev_lock_cid == prior lock CID
```

`op_count` is retained as a cheap tripwire, not as the proof. The chain hashes are the proof. Steps 1–3 are Data plane and write no control state — layer uncollapse, §8.2.5.

The audit log is append-only in the sense that rewriting a past entry invalidates every `op_hash` after it, up to and including the lock. Deletion from the tail is caught by `prev_lock_cid`. Neither is prevented, because the vault does not hold K and cannot hold a sealing key. The log is tamper-*evident*, not tamper-proof. Saying otherwise would be the coat §15 refuses.

### **8\.2\.4 Draft target Lean — `KXiVaultReceipt.lex.tex`**

```lean
module Foundry.Storage.KXiVaultReceipt

inductive ReceiptState where
  | created     -- 0 signatures
  | signedK1    -- 1 signature
  | signedBoth  -- 2 signatures from 2 distinct pubkeys
  | verified    -- validated against the control-plane predicates
  | rejected
  deriving Repr, DecidableEq

inductive ReceiptAction where
  | signK1 | signK2 | verify | reject
  deriving Repr, DecidableEq

/-- Linear progression. Every other transition is refused. -/
def transition : ReceiptState -> ReceiptAction -> Option ReceiptState
  | .created,    .signK1 => some .signedK1
  | .signedK1,   .signK2 => some .signedBoth
  | .signedBoth, .verify => some .verified
  | .signedBoth, .reject => some .rejected
  | _,           _       => none

/-- Signatures accumulated before validation. -/
def sigCount : ReceiptState -> Nat
  | .created => 0
  | .signedK1 => 1
  | .signedBoth => 2
  | .verified => 2
  | .rejected => 0

theorem verified_requires_signed_both (s : ReceiptState) (a : ReceiptAction)
    (h : transition s a = some .verified) : s = .signedBoth := by
  cases s <;> cases a <;> simp [transition] at h

theorem verified_implies_two_sigs (s : ReceiptState) (a : ReceiptAction)
    (h : transition s a = some .verified) : sigCount s >= 2 := by
  subst h
  simp [sigCount]
```

Two corrections, both in the ledger. The Blueprint's `verified_implies_two_sigs` stated `s = .verified → true` and closed it with `trivial`. That is not an invariant; it is a tautology that compiles whether or not the state machine is correct, and it would have satisfied a zero-sorry gate while proving nothing. C-10.

The Blueprint's `transition` also admitted `.created, .verify => none` correctly by the catch-all, but recorded no `distinctKeys` check, so a receipt could reach `.verified` with two signatures from one pubkey unless the caller supplied the check. The state machine is therefore paired with `isAccept`, not a substitute for it: `.verified` means two signatures were presented and the predicates were run, never that two persons signed. The two facts are recorded separately, in `sigCount` and in `isAccept`, and a reader may not read one as the other.

### **8\.2\.5 Draft target Lean — `LayerUncollapse.lex.tex`**

```lean
module Foundry.Invariants.LayerUncollapse

inductive Layer where
  | data | control | tooling | publish
  deriving Repr, DecidableEq

inductive Operation where
  | store       (c : CID)
  | preimage    (c : CID)
  | pin         (c : CID)
  | accept      (r : ReceiptID)
  | exportCheck (c : CID)
  | compile     (m : ModuleId)
  | verify      (m : ModuleId)
  | publish     (p : Path)
  deriving Repr, DecidableEq

def operationLayer : Operation -> Layer
  | .store _ | .preimage _ | .pin _ => .data
  | .accept _ | .exportCheck _     => .control
  | .compile _ | .verify _         => .tooling
  | .publish _                     => .publish

def mutates (op : Operation) (target : Layer) : Bool :=
  operationLayer op == target

theorem no_cross_layer_mutation (op : Operation) (target : Layer)
    (h : operationLayer op <> target) : mutates op target = false := by
  simp [mutates, h]

/-- Data-plane operations carry no control mutation. -/
def layerUncollapsed (op : Operation) : Bool :=
  match op with
  | .store _ | .preimage _ | .pin _        => true
  | .accept _ | .exportCheck _            => false
  | .compile _ | .verify _ | .publish _   => true
```

Three corrections. The Blueprint's `mutates` was used in `no_cross_layer_mutation` but never defined, so the theorem had no statement — C-11. Its `layerUncollapsed` matched only four of eight constructors, so it was not a total function and would not have compiled — C-08. Its `no_cross_layer_mutation` closed by `cases op <;> simp ... at *` over an undefined `mutates`, which is a tactic that succeeds loudly on nothing.

`layerUncollapsed .accept _ = false` and `operationLayer (.accept _) = .control` are two different claims and are kept in two different places. The first says a data-origin accept is refused; the second says accept is a control operation. A vault-origin accept fails the first. A control-origin accept is legitimate and must not be blocked by confusing the two — that confusion is the "vault can never Accept" coat, which is a different error from "the vault is not the control plane."

## **8\.3 Tooling plane impact**

Tooling detail, the four-stage pipeline, the defect-plant registry, and the lock schema are on `PM-KXI-005` §8. From this paper, the tooling plane holds two constraints:

1\. No new adapter is named for license or hide (`PM-KXI-003` §5, `PM-KXI-005` §4). The Blueprint adds none, and none may be added to satisfy a §8 command.

2\. Sign and verify adapters are tools. `PM-KXI-005` Stage 4 runs `just vv`; Stage 3 runs defect plants. Neither is a person, and a green matrix is not a quorum. `prismpm_is_compiler() = true`, `prismpm_is_control_plane() = false`.

## **8\.4 Publisher surface impact**

`foundry-web` consumes a verified producer revision and renders flags. Structure and manifest schema are on `PM-KXI-005` §8.3. From this paper:

`keyCount` is displayed, never `distinctKeys` as an Accept signal. A View that renders `k1_seated: true, k2_seated: true` next to no `accept` flag invites the reader to do the subtraction and get the wrong answer. `accept` is the only accept-adjacent flag a View renders, and it renders the predicate result, not a recomputation.

## **8\.5 Cross-layer dependencies**

```
FROM ->      Data     Control   Tooling   Publish
-----------  -------  --------  --------  -------
Data         .        flags     source    digest
Control      gate     .         rules     flags
Tooling      verify   compile   .         manifest
Publish      consume  read      verify    .
```

Invariant: no layer mutates another layer's state. Every arrow is a read, a digest, or a predicate result. A layer that needs a decision from another layer asks; it does not reach.

Flag propagation is one-directional and terminating:

```
k3-vault/vault.json
      -> KXiVault.lex.tex        (predicates over vault state)
      -> KXiVaultView.lex.tex    (read-only projection)
      -> FLAG REGISTRY {cid, pinned, accept, keyCount}
      -> PrismPM verify | CONFORMANCE MATRIX | foundry-web display
```

The registry is a projection, not a source. Nothing writes a flag that a predicate did not produce. A hand-edited `vault-status.html` showing `accept: true` is a publisher defect and a stop condition, independent of whether the underlying state is real.

### **8\.5\.1 Sequencing: vault before transaction**

The vault is constructed before any transaction it will hold. `KXiVault.lex.tex` and the `k3-vault` directory do not depend on `049c` existing, on K2 being seated, or on any ADR being pinned. This is why the domain separator is vault-scoped (§8.1.2): the second seat needs a vault to sign *into*, and a vault that waits for a transaction has nothing to sign into.

Corollary, and the reason the §20 precision question stays open: building the vault does not move the person track. A green `just vv` with `pinned = false`, `accept = false`, and K2 VACANT is the correct end state of the software increment, not a shortfall in it.
