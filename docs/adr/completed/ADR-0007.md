**Answer: a frozen plain-text file. Not the `.docx`. Not a re-derivable normalization.**

The `.docx` is provenance. The frozen text is the signed artifact. The observed `.docx` SHA-256 `4050d4c4…d0b9` is recorded as provenance, not as the pin.

## Why neither of the other two candidates holds

```
| Candidate                       | Stable across saves?                                                                                                        | Legible to a stranger? | Two honest people agree?                                                                                     | Verdict                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `.docx` as saved                | **No** — `docProps/core.xml` (`dcterms:modified`, revision), rsid entries, zip timestamps, compression all shift on re-save | No — needs unzip       | No — same text, different bytes                                                                              | Provenance only                                                                            |
| Renormalized UTF-8 body         | Only if the extractor is bit-exact                                                                                          | Yes                    | No — two extractors disagree on headings, tables, footnotes, comments, tracked changes, NFC form, LF vs CRLF | Refused as pin                                                                             |
| Frozen plain-text file          | **Yes** — bytes are frozen                                                                                                  | Yes                    | **Yes** — both hash the same file                                                                            | **Canonical**                                                                              |
| Revision pinned by its own hash | Yes                                                                                                                         | Yes                    | Yes                                                                                                          | This is the *result*, not the *method*. Still needs one of the above to produce the bytes. |
```

The circular candidate is real: “the bytes whose hash is X” identifies the text only after you already have it. It is the identifier, not the construction. You still need a procedure that produces the bytes.

## Who signs the ADR

```
| Role                     | Signs ADR?                                           | Signs Accept preimage?    |
| ------------------------ | ---------------------------------------------------- | ------------------------- |
| **Architect** (proposer) | Yes — attests “these frozen bytes are the 049c text” | Yes — step 4              |

```

The architect proposes the canonical bytes. The second hand disposes by signing or refusing. That is the refuse-a-bind mechanism. If the architect door is UNCLEAR, the board must either seat it or name a different **canonicalization authority** to propose the bytes. Either way, K2 remains vacant and is the only door that can Accept.
