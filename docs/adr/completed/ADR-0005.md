**Reframe first.** The vault is K3. It holds content addresses and memory — not HMAC \(K\), not a K2 seed, not an ML-DSA-44 seed. The crown jewels live in three other doors, all of which are either workshop custody or **vacant**. So the container does not need to be a fortress. It needs to be **legible, forkable, offline-capable, and kill-switch-free**. That is a different optimization target than “maximum security,” and it changes the ranking.

The binding constraint is not the container. It is the **vacant K2 seat**. No container makes the second hand exist. Container engineering before K2 is seating is polishing a lock on a door with no second key.

## The disqualifiers, in order

1. **Vendor kill switch on the vault** → Snap, Chrome Web Store, any store-hosted extension, any policy-controlled channel. The vault cannot live there.
2. **No offline mode** → browser extensions, online-only PWAs. They are views.
3. **No native crypto libs** → WebCrypto-only environments. They cannot run HMAC with a loaded key, cannot use libsodium, cannot ever seat ML-DSA-44.
4. **Cannot be rebuilt and audited from source** → anything with remote code, CDN fetches, or opaque build pipelines.
5. **Holds secrets it shouldn't** → any container that tempts you to put HMAC \(K\), K2 seed, or ML-DSA-44 seed in it. That is a custody error, not a container feature.

Everything that survives all five is a **vault candidate**. Everything that fails any is a **view** or is refused.

## The composite that survives all five

The honest best path is not one container. It is a **layered stack where each layer has one job and one refuser**.

```
┌─────────────────────────────────────────────────────┐
│ View layer (disposable, no secrets) │
│ Tauri / GTK / Qt / localhost web / thin extension │
└──────────────────────┬──────────────────────────────┘
│ reads only
┌──────────────────────▼──────────────────────────────┐
│ Vault layer (K3, legible, forkable) │
│ Files + CLI (sha256sum, JSON index, QR export) │
│ Optional: Nix/Guix or AppImage for distribution │
└──────────────────────┬──────────────────────────────┘
│ digest out
┌──────────────────────▼──────────────────────────────┐
│ Accept layer (vacant, hardware-backed) │
│ K2 key on YubiKey/Nitrokey or air-gapped Qubes │
│ Held by named other person. Signs the digest. │
└──────────────────────┬──────────────────────────────┘
│
┌──────────────────────▼──────────────────────────────┐
│ Cold layer (offline) │
│ Paper / steel shards. QR transfer. Indexed by vault│
└─────────────────────────────────────────────────────┘

HMAC K ── workshop custody. Not in any layer above.
```

```
| Layer  | Job                      | Refuser                       | Canonical form                       |
| ------ | ------------------------ | ----------------------------- | ------------------------------------ |
| View   | Show, export, display QR | Sandbox + no secrets          | Disposable. Any UI.                  |
| Vault  | Content address, memory  | Filesystem + no network       | Directory + CLI                      |
| Accept | Sign the digest          | Second cryptographic identity | Hardware token or air-gapped machine |
| Cold   | Survive catastrophe      | Physics                       | Paper, steel                         |
| Kernel | Authenticate 049c limbs  | Workshop keyholder            | HMAC \(K\), offline                  |
```

Each layer refuses independently. No layer can do another layer’s job. The vault cannot Accept. The view cannot hold. The token cannot index. The paper cannot compute.

## Why “files + CLI” beats Flatpak and PWA as the vault

```
| Property                | Files + CLI                 | Flatpak                     | PWA                               |
| ----------------------- | --------------------------- | --------------------------- | --------------------------------- |
| Vendor can kill it      | No                          | No                          | Yes                               |
| Works with no network   | Yes                         | Yes                         | Partial                           |
| Rebuildable from source | Yes, trivially              | Yes, with runtime           | No                                |
| Forkable by a stranger  | Yes — copy the directory    | Yes — repackage             | No                                |
| Air-gapped              | Yes                         | Yes                         | No                                |
| Survives OS reinstall   | Yes — it's files            | Reinstall Flatpak           | No                                |
| Audit surface           | `sha256sum`, JSON, ~500 LOC | Manifest + runtime + portal | Browser + service worker + vendor |
| Cold-capable            | Yes — print the index       | No                          | No                                |
| Needs a store           | No                          | Optional                    | Yes                               |
```

The Flatpak is a fine **distribution wrapper** around the CLI. The PWA is a fine **view** if it never holds anything. Neither is the vault. The vault is a directory and a small program that anyone can read and copy.

## The second-person device is a different problem

The K2 signer is not a vault. It is a **signing ceremony**. That device should be:

- **Hardware-backed** (YubiKey, Nitrokey, SoloKey, smartcard) or **air-gapped** (Qubes AppVM, old laptop with no radio, Tails/Whonix if amnesic is wanted).
- **Single-purpose**. No browser, no email, no store.
- **Held by the named other person**, not the inventor, not the architect keyboard.
- **Physically separate** from the vault device.

The K2 key never touches the vault container. The vault produces a digest; the token signs it; the vault records the receipt. That is the two-person receipt control plane in hardware.

## What this does not do

- Does not name K2. PM-K2-001 stays non-vacant only when a legal person signs.
- Does not Accept 049c. 049c stays Proposed.
- Does not evidence any Day Zero row. ev(c)=1 still needed for authority, scope, public facts, capacity, custody, pilot.
- Does not open Week 1.
- Does not move funds. G=0.
- Does not put Poseidon2 live. Zero live-seal sites.
- Does not put ML-DSA-44 or ML-KEM-512 on the fuse. Zero crates.
- Does not turn A into permission to ship surfaces. A is a lock, not a ship order.

## Decision procedure (for any future container)

Ask, in order:

1. Can a vendor disable it? → If yes, it cannot hold the vault. View only.
2. Does it work with no network? → If no, view only.
3. Does it have native crypto libs? → If no, view only.
4. Can a stranger rebuild it from source and copy the data out? → If no, refused.
5. Does it tempt you to hold HMAC \(K\), K2 seed, or PQ seed? → If yes, custody error. Refuse the container.
6. Does the second cryptographic identity still get to refuse the bind? → If no, out of scope even if it compiles.

Everything that passes 1–6 is a vault candidate. Everything else is a view, a wrapper, or refused.

## Precision question

Is the canonical vault artifact a **directory of files plus a small, rebuildable CLI** — forkable, air-gappable, kill-switch-free — or does it require a GUI container to count as shipped, because only the first can be refused by the second hand without a vendor, a store, or a runtime in the loop, and the second makes the container the refuser instead of the person.
