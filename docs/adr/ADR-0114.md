# ADR-0114: Constraint Trait Generic Over Content Type

**Status:** Accepted

## Context

The `Constraint` trait in `crates/ri1-core/src/constraints.rs` was defined as `fn check(&self, text: &str) -> ConstraintResult`, accepting only text. The crate README claims multimodal capability (text, code, image, audio, signals), but constraint evaluation had no path for non-text content. Any future modality was forced to serialize to text before constraint checking, with no trait infrastructure for binary, image, audio, or structured-code constraints.

## Decision

Make `Constraint` generic over content type `T` with default `T = str`:

```rust
pub trait Constraint<T = str>: Send + Sync {
    fn name(&self) -> &'static str;
    fn check(&self, content: &T) -> ConstraintResult;
}
```

This is backward-compatible: existing `Box<dyn Constraint + Send + Sync>` resolves to `Box<dyn Constraint<str> + Send + Sync>` via the default parameter. New multimodal constraints use explicit type parameters, e.g., `Box<dyn Constraint<[u8]> + Send + Sync>` for binary content.

`ConstraintResult` gains helper constructors: `pass(name)`, `fail(name, message)`, `fail_soft(name, message)`.

## Consequences

- Existing `Constraint` implementations continue to compile unchanged
- Multimodal constraint evaluation infrastructure exists; first consumer is `MaxBytes(usize)` operating on `&[u8]` (defined in `Constraint` trait doc example)
- Engine dispatch for multimodal content requires a separate design (not addressed here; see ADR-0115)
- The crate README is updated to reflect: text-based constraint evaluation is the default; multimodal constraint evaluation is infrastructure-supported but not yet implemented for all modalities
