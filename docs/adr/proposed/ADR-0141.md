# ADR-0141: Every Gate This Change Added Reaches the Developer Who Has to Run It

**Status:** Proposed

## Context
ADR-0139 added `scripts/check_submodule_integrity.py`, which grades every pinned commit `ADVERTISED`, `UNVOUCHED` or `GONE`, and wired it into `.github/workflows/submodule-gate.yml`. Applying the Phase Mirror axes to that implementation finds the tension the record did not address: it is not that the gate is wrong, it is that almost nobody will run it.

`control desired vs available` is the axis here, and the gap is concrete. The gate is reachable from three surfaces: the GitHub Actions workflow, a manual `python3 scripts/check_submodule_integrity.py`, and a manual `--root packages` invocation for the nested repository. It is absent from the root `Justfile`, whose `vv` recipe is the acceptance gate this repository already documents and which runs `lean-sorry-check` but nothing about submodules; it is absent from the `Makefile`, whose `adr-sorry-check` and `adr-index` targets establish that local gate entry points are the convention here; and it is absent from `scripts/verify_governance_gates.py`, the one script that aggregates governance checks and the surface `compliance/governance/DISSONANCE-REGISTER.json` names as its own `enforcement` field. A gate that lives only in CI can be green locally and red remotely, which means the person best placed to prevent the defect is the person not running it. `packages/` is worse: it is a separate repository with no workflow at all, so the only way to check its pins is to remember a flag on a script in its parent.

This is the same class of finding `docs/adr/proposed/ADR-PML-072.md` already recorded for the Phase Mirror loop itself, which runs above the formal ADR model rather than inside it. A new gate that repeats the pattern is not a new gate in the governance sense; it is a second ungoverned control surface. The register now carries this as `D-20`, severity High, because a named tension that nothing enforces is exactly what the Phase Mirror loop's own `some-true` rows forbid.

## Decision
The submodule gate joins the surfaces a developer already runs, rather than adding a fifth place to remember. A `submodule-check` recipe is added to the root `Justfile` and a `submodule-check` target to the `Makefile`, both invoking `scripts/check_submodule_integrity.py`, and `vv` gains the recipe so the documented acceptance gate covers it. `scripts/verify_governance_gates.py` gains the submodule gate as a tenth enumerated gate, reported in the same `N/10 gates passed` line as the nine it already aggregates, so a failure surfaces in the single command the dissonance register points at. `--probe-remote` is used in the aggregate gate, because the stranded-pin class it exists to catch is invisible offline, and the remote probe is what makes `GONE` distinguishable from a local checkout that merely has not run yet.

One copy of the gate serves both repositories. `packages/` receives no copy of the script and no second lockstep reader; the `--root` flag added by ADR-0139 is what checks it, and the aggregate gate invokes it for both roots. Two copies of a control surface is the failure this whole line of work exists to close, so duplicating the gate into the nested repository would reintroduce it in the shape of the fix.

The gate stays fail-closed and stays advisory where ADR-0139 and ADR-0140 made it so: `GONE` is an error unless an acknowledgement naming a tracking ADR exists, an acknowledgement goes stale — and therefore red — the moment its condition resolves, and `UNVOUCHED` is a warning that `--strict` promotes. Wiring the gate into more surfaces does not grant it more authority than it already has.

## Consequences
* A developer running `just vv` or `make submodule-check` now runs the submodule gate, so the stranded-pin class is caught before a push rather than after it
* `verify_governance_gates.py` reports the submodule gate as one of its enumerated gates, so the dissonance register's `enforcement` field becomes true for `D-20` rather than aspirational
* `packages/` becomes checkable from a single command instead of a remembered flag, and the two repositories cannot disagree about a pin because one implementation reads both
* The aggregate gate now requires network access to grade pins, so a fully offline `verify_governance_gates.py` run cannot grade `GONE` versus merely-unchecked; the offline path is retained and reports pins as unverified warnings rather than silently passing, which keeps an air-gapped run honest about what it did not check
* `vv` grows by one recipe, so its wall-clock time grows by the remote probe latency for four submodules; the probe is network-bound and this is accepted rather than cached, because a cached pin grade is a stale pin grade
* `D-20` moves from `open` to `resolved` only when `verify_governance_gates.py` itself reports the submodule gate passing, which is the proof the register's `proves` field will name
* Packages still has no CI of its own, so its pins are checked only when The-Foundry's aggregate gate runs against it; a future independent check for that repository remains open and is not closed by this record
