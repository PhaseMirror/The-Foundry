# ADR-0143: One ADR Namespace, One Index, and a Plan Registry That Can See Every Record

**Status:** Proposed

## Context
Three measured facts about this repository's ADR surface disagree with each other, and all three are `intent vs operating incentives`: documents present themselves as authoritative indexes while disagreeing with the data they index.

First, `docs/adr/README.md` calls itself the ADR Ledger and states `Total ADRs: 28`. `docs/adr/registry.json` holds **43** records. The README's table stops at ADR-0120 and omits ADR-0128 through ADR-0138 entirely, so the two surfaces are not off by a rounding error; a reader consulting the README cannot discover thirteen accepted records, including ADR-0131 and ADR-0138, both of which other records cite as governing. The README is a generated artifact of `scripts/generate_adr_index.py`, and regenerating it is a one-command fix nobody has run.

Second, `ADR-PML-NNN` numbering is already triplicated with different content under the same id. `ADR-PML-005` exists in `docs/adr/`, in `docs/adr/proposed/` and in `docs/adr/completed/`, as three different documents. The research that located the Phase Mirror methodology found `proposed/ADR-PML-058.md` to be a control-surfaces tension while `completed/ADR-PML-064-*.md` asserts that `058`..`063` are the LexLean plane — a claim the files themselves contradict. Those LexLean records turned out to live only in the retired `packages/LexLean` clone and are now preserved at `docs/adr/lexlean/`, a fourth location, chosen precisely because the numbers were taken.

Third, and worst for enforcement, `phase_mirror_loop.py`'s `export_plan_registry()` enumerates ADR records with a non-recursive `os.listdir` of `docs/adr/`. Every record under `proposed/`, `completed/` and the new `lexlean/` namespace is therefore invisible to `state/adr_plan_registry.json` — and that file is `include_str!`-compiled into `packages/rust/adr-verifier/src/lib.rs`, which enforces the boundary rules `RequiredAdrNotAccepted` and `LeakedClosedAdr` against it. The 227-file `proposed/` series has never been subject to a single one of those rules. This record's own `ADR-0139`, `ADR-0140` and `ADR-0141` are in `proposed/` and are equally unenforced.

The incentive that produced this is legible: writing a record into a subdirectory is frictionless, indexing it is not, and nothing fails when a record is unindexed. A record that no tool can reach is not governed, and the repository's own `ADR-PML-072` already recorded the general form — "generates ADRs without formal governance" — without connecting it to the indexing failure that causes it.

## Decision
`docs/adr/README.md` is regenerated from `docs/adr/registry.json` rather than maintained by hand, and a gate asserts the two agree on both record count and id set, so the ledger cannot drift again. `registry.json` becomes the single source for non-PML records and the README a rendered view of it.

`ADR-PML-NNN` numbering is unified. The three existing numbers are resolved by directory precedence — `proposed/` is the live series, `completed/` records the disposition in a `## Resolution` section rather than in the filename, and the top-level `ADR-PML-001`..`011` files generated by the loop are retired into `proposed/` — after which `next_plan_number()` scans every ADR directory and returns `229`, above the highest number in use anywhere. The collision is resolved by renaming, not by deleting: no record is dropped to make the numbering tidy, because a duplicate id resolved by discarding one copy is indistinguishable from a record lost.

The plan registry enumerates recursively. `export_plan_registry()` walks the ADR directories rather than one, so every `ADR-PML` record reaches `state/adr_plan_registry.json` and therefore the Rust boundary rules. Because that file is compiled into a binary by `include_str!`, the registry is regenerated and the consuming crates rebuilt in the same change, and the record states plainly that a stale registry means the binary enforces rules against months-old data — which is a `some-true` claim about enforcement that must not be made while a stale file is committed.

Finally, `docs/adr/lexlean/` is kept as a distinct namespace with its `PROVENANCE.md` rather than folded into `proposed/`, because folding it in would recreate under `ADR-PML-058`..`062` the exact collision that namespace exists to avoid. The five recovered LexLean records are registered in `registry.json` with their real paths so they are reachable by the same tooling as everything else, even though their numbers are shared with another series; the shared number is recorded in the record's `supersedes`-adjacent metadata rather than hidden.

## Consequences
* `docs/adr/README.md` stops under-reporting by thirteen records, and a gate fails if it ever disagrees with `registry.json` again
* Every `ADR-PML` record becomes visible to the Rust `adr-verifier` boundary rules for the first time, which will surface pre-existing violations that were previously impossible to detect — the gate is expected to go red on first run and those findings are real, not regressions introduced here
* `next_plan_number()` returning 229 removes the collision hazard that made a non-dry Phase Mirror run unsafe, which is the precondition ADR-0142 needs
* The ADR-PML series is renumbered across three directories, producing a large, mechanical diff whose review value is low; it is deliberately isolated in its own change so it can be reviewed for completeness of renames rather than for content
* `state/adr_plan_registry.json` and the compiled consumers must be rebuilt together, and a committed stale registry is a silent enforcement gap that no existing gate detects; the rebuild is therefore part of this decision, not a follow-up
* `ADR-0131` and `ADR-0138` become discoverable from the README, so records that cite them as governing stop citing something a reader cannot find
* `docs/adr/lexlean/` remains a fourth namespace, which is honest about a genuine historical split but leaves four directories to search; collapsing it is deferred rather than faked, since the alternative is reintroducing a duplicate number
* The untracked `accepted/` to `completed/` migration visible in the working tree during this work is the same incentive acting on status directories; this record does not resolve that migration and it must not be committed alongside the renames
