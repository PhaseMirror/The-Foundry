# ADR-RML-167: Artifact identity is hand-maintained and diverges; a template sits in the wrong crate

## Status
Proposed

## Triage (time-aware phase mirror)
- Subject: `packages/Agency/agency-server/wasm-pkg/package.json`, `packages/PhaseMirror/phase_mirror_wasm/templates/retention_policy.yaml`
- Verdict signature: `50db02c06f74b6cd`

## Context and Problem Statement

Two low-severity items that compound: the crate's published identity is maintained
by hand on both sides of a copy boundary, and the crate carries a template that
belongs to a different subsystem.

### The publish boundary has two hand-maintained versions

The crate is published to `packages/Agency/agency-server/wasm-pkg/`, which declares:

```json
{
  "name": "phase_mirror_wasm",
  "version": "0.1.0",
  "files": [
    "phase_mirror_wasm_bg.wasm",
    "phase_mirror_wasm.js",
    "phase_mirror_wasm.d.ts"
  ]
}
```

Against `packages/PhaseMirror/phase_mirror_wasm/Cargo.toml`:

```toml
name = "phase_mirror_wasm"
version = "1.0.0-alpha"
```

Two version strings, `0.1.0` and `1.0.0-alpha`, for one artifact. Neither
references the other, and nothing asserts they match. The `files` list names three
artifacts, none of which exist: no `wasm-pack build` has been run, and there is no
`pkg/` directory in the package.

`package.json` is hand-maintained rather than generated. `wasm-pack` normally emits
a `package.json` alongside the artifacts; this one was written by hand and will
silently drift on every release. Nothing in the tree compares the two versions, so
the drift is invisible until a consumer installs `0.1.0` of a `1.0.0-alpha` crate.

Per ADR-RML-163 and ADR-RML-164 the artifact contents and names change as part of
that work, so this is the moment to fix the boundary rather than after.

### An ESI retention template sits in a WASM crate

`packages/PhaseMirror/phase_mirror_wasm/templates/retention_policy.yaml`:

```yaml
default_retention_days: 365
categories:
  emails: { retention_days: 730, litigation_hold: false }
  contracts: { retention_days: 1825, litigation_hold: true }
  logs: { retention_days: 180, litigation_hold: false }
risk_levels:
  critical: "Critical"
  high: "High"
  medium: "Medium"
```

This is an Electronic Stored Information retention policy with litigation-hold
flags. That domain belongs to `phase-mirror-mcp/src/tools/evaluate_esi_risk.rs`,
which is where `risk_levels` is consumed and where the retention categories have
meaning.

Nothing in `phase_mirror_wasm` reads it. There is no YAML parser in the dependency
list, so it cannot be read: no `serde_yaml`, no `yaml-rust`. The file's own header
says "Packages should copy this file into their `templates/` directory and adjust
values per domain-specific needs", which describes it as a source template to be
copied, not an input to the crate holding it. It is the only file in that
`templates/` directory.

The comment "Do NOT edit risk enum values; they must match the engine output
(Critical, High, Medium)" is a real coupling instruction, and it is in a package
that has no relationship to the engine it constrains. The instruction will be
followed by whoever finds the file, and it will not be enforced anywhere.

## Considered Options

### Option 1: Generate the publish manifest, move the template to its owner
- Pros: Version drift becomes impossible rather than merely checked. The retention
  template reaches the subsystem whose engine it constrains.
- Cons: Requires a `wasm-pack build` to run at publish time, which is not happening
  today.

### Option 2: Add a consistency check to CI
- Pros: Cheap, no build changes.
- Cons: A check that compares two hand-maintained strings. It reports drift after
  the fact rather than preventing it, and it will need re-adding whenever someone
  edits a manifest. Insufficient on its own.

### Option 3: Leave both as-is
- Pros: No work.
- Cons: The version divergence is already present and will widen with the
  ADR-RML-163 and ADR-RML-164 changes. The template stays in a crate that cannot
  read it.

## Decision Outcome

Option 1.

1. `wasm-pkg/package.json` is generated by `wasm-pack build --out-dir` during
   publish, not hand-maintained. The hand-written file is deleted. A small
   `publish.sh` performs build, version propagation from `Cargo.toml`, and the size
   assertion from ADR-RML-166.
2. The version source of truth is `Cargo.toml`. `1.0.0-alpha` is the current value
   and `0.1.0` in the npm manifest is treated as a defect, not as a version.
3. `templates/retention_policy.yaml` moves to
   `packages/PhaseMirror/phase-mirror-mcp/templates/retention_policy.yaml`, next to
   `evaluate_esi_risk.rs` which consumes the risk levels it declares.
4. The `risk_levels` coupling in that file becomes a test in `phase-mirror-mcp`
   asserting the engine's emitted risk strings match the declared enum, so the
   comment's requirement is enforced rather than advisory. This is the correct
   home for the instruction; a YAML comment in an unrelated package was never able
   to enforce it.

## Consequences

### Positive
- One version string. The publish step cannot produce a mismatch.
- The retention template sits with the engine it constrains, and the coupling it
  describes becomes testable.
- The 2 MiB size assertion from ADR-RML-166 gets a natural home in the publish
  script, where the artifact exists.

### Negative
- Publishing becomes a build step rather than a file copy. Anyone who was copying
  files manually must run the script.
- If `wasm-pack` is not available in the publishing environment, the manifest
  cannot be generated and the fallback is Option 2. This should be checked before
  committing to Option 1.
- Moving the template is a cross-package change for a file that nothing currently
  reads, so the diff is larger than the behavioural change. Worth doing precisely
  because nothing depends on its current location.

### Verification Strategy
`grep -rn '"version"' packages/Agency/agency-server/wasm-pkg/package.json` matches
the value in `Cargo.toml` after a publish run. A test in `phase-mirror-mcp` asserts
the risk enum matches the engine output, and fails if either changes alone. A
`git status` check after a publish run shows no modification to the manifest,
confirming it is generated.
