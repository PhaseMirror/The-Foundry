# ADR-0117: OperatorClass as Documented Taxonomy with Dead Code Cleanup

**Status:** Accepted

## Context

`OperatorClass` in `crates/ri1-core/src/constraints.rs` is an enum with 30 variants spanning field-phase operators (001-019), measurement (020), conditionals, violations, and index modifiers. Variants are used exclusively as labels in `ResonanceEvent.operator` for influence scoring and negotiation edge computation. No `match` or dispatch on `OperatorClass` variants drives behavior. Adjacent dead-code items (`op()`, `cond()` helper functions, `DeltaOutcome.irreversible` field, `RuleViolation` struct) were discovered and removed.

## Decision

1. Document `OperatorClass` as a taxonomy for influence scoring and event labeling, explicitly NOT a dispatch table. Operator behavior lives in `OperatorGate` implementations.
2. Remove dead-code items:
   - `op()` and `cond()` helper functions in `ri1-symbolic-meta/src/lib.rs`
   - `DeltaOutcome.irreversible` field in `ri1-symbolic-meta/src/lib.rs`
   - `RuleViolation` struct in `ri1-symbolic-meta/src/interaction/rules.rs`
3. Add validation test `operator_class_taxonomy_complete()` confirming all 30 variants exist and are debug-formattable
4. Add `ConstraintResult::pass/fail/fail_soft` constructors for ergonomic constraint creation

## Consequences

- All dead-code compiler warnings eliminated from workspace
- OperatorClass taxonomy is documented and validated
- Future operator additions must be documented as taxonomy entries
- Tests confirm taxonomy completeness (30 variants)
