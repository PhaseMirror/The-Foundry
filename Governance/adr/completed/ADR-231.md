# ADR-231: Production-Grade Hybrid Verification Pipeline for Lean 4 and Rust/Kani

- Status: accepted
- Date: 2026-07-23
- Owners: Multiplicity Foundation
- Tags: #lean, #kani, #rust, #verification, #hybrid-pipeline, #provably-correct

## 1. Context

Formalizing complex mathematical physics and high-assurance runtime architectures (such as Complex Gravitational Coupling, Prime-Indexed Recursive Tensor Mathematics (PIRTM), and Operator-First Arithmetic) requires absolute logical rigor. Traditional verification approaches often force a choice between unexecutable abstract mathematics or unprovable floating-point software systems.

To resolve this, we adopt a **hybrid verification pipeline** that decouples semantic proof from bounded computation:

1. **The Lean 4 Core (`/lean`)**: Implemented entirely under a strict **zero-Mathlib, zero-sorry** constructivist mandate. It provides foundational typeclasses, endomorphism categories, and invariant theorems.
2. **The Rust/Kani Engine (`/crates`)**: Serves as the executable image of the mathematical core, utilizing Kani bounded model checking and exact rational intervals (`Rat`) to eliminate IEEE-754 floating-point serialization drift.
3. **The Governance-as-Compilation Pipeline (`/scripts`, `/contracts`)**: Automatically generates verification harnesses, enforces contractive upper bounds ($L_\Phi < 1$ or $\lambda_p L_p < 1$), and triggers fail-closed `SIG_GOV_KILL` exceptions if unverified drift is detected.

## 2. Decision

We formally ratify the **Provable-Contracts Architecture** as the exclusive standard for system verification across all repository modules.

### Core Rules & Invariants

* **No Mathlib Dependency in Core:** Lean modules must operate within a minimal constructivist core to ensure deterministic compilation, reproducible proofs, and explicit axiom auditing (`Axioms.lean`).
* **Rational Interval FPU Bypass:** All critical arithmetic values and bounds exchanged between Rust runtime and Lean proofs must use exact rational interval representations (`Rat`) rather than raw `f32`/`f64` floats to prevent hardware-dependent rounding tears.
* **Contractive Bounding ($L_\Phi < 1$):** Every operator composition or state transition vector must satisfy strict Lipschitz contraction constraints, guaranteed via Kani symbolic execution up to pre-registered dimensions.
* **Fail-Closed CI Enforcment:** Pull requests that violate contraction thresholds, introduce unverified axioms without an explicit manifest (`alp_sorry_manifest.json`), or break cross-language binary parity will automatically fail CI via `scripts/validate_zero_drift.sh`.

## 4. Consequences

### Positive

* **Zero Trust in FPU:** Bounded model checking via Kani and rational interval arithmetic ensure that systems code is verified against exhaustive state spaces rather than probabilistic spot-checks.
* **Audit-Tight Provenance:** Every state transition is bound to an immutable native ACE certificates and triple lock governance (Write-Once-Read-Many) audit log and anchored via Prime-Weighted Execution Hashing (PWEH) or Poseidon2 commitments.
* **Regulatory Alignment:** Satisfies rigorous compliance standards (such as EU AI Act Annex IV technical documentation and NIST AI RMF tracking) by maintaining deterministic traceability from high-level proofs down to execution telemetry.

### Negative / Trade-offs

* **Initial Development Overhead:** Writing mathlib-free Lean 4 proofs requires constructing foundational algebraic types explicitly, increasing upfront engineering effort.
* **Bounded Scope:** Kani verification is bounded by pre-registered dimension limits (e.g., matrix dimensions up to $N = 12$ or $32$), requiring complementary induction theorems in Lean for infinite-domain generalizations.

## 5. Verification Strategy & Milestone Implementation Plan

1. **Phase 1: Formal Specification** — Draft core algebraic structures in Lean 4 with zero sorrys, explicitly defining endomorphism categories and initial algebras.
2. **Phase 2: Runtime Binding** — Implement parallel Rust traits (`Operator`, `EndomorphismRule`) and exact interval handlers.
3. **Phase 3: Automated Proof-Contracts Generation** — Use YAML contracts in `/contracts/` to generate Kani harnesses and cross-verify boundary limits.
4. **Phase 4: CI Gating** — Run `validate_zero_drift.sh` on every pull request to enforce byte-exact parity and strict contractivity.
